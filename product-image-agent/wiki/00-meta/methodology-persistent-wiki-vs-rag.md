# 方法论 - Persistent Wiki vs RAG

> 基于 Karpathy LLM Wiki 思路：让 LLM 维护持久化、互联的 Markdown 知识库。

## 核心问题：标准 RAG 的局限

```
用户提问 → 检索相关片段 → LLM 临时拼装答案 → 会话结束 → 知识消散
```

每次对话 LLM 都**从零发现**知识，无法：
- 积累跨会话的研究成果
- 追踪信息更新与矛盾
- 形成可浏览、可链接的知识图谱

## Persistent Wiki 方案

```
新来源 → LLM 阅读 → 提取关键信息 → 更新/创建实体页 → 修订摘要 → 标注矛盾 → 写入 Changelog
```

### 五条维护原则

1. **实体优先**：每个重要概念一个页面（如 [[UPS 统一产品描述锚]]），而非按来源堆叠
2. **双向链接**：用 `[[wikilink]]` 连接相关实体，Obsidian Graph 可视化关系
3. **增量更新**：新信息合并进已有页面，修订「摘要」区块，不重复创建
4. **矛盾显式化**：来源冲突时写入「矛盾与待验证」，不 silently 覆盖
5. **变更有迹**：每次更新记录到 [[更新日志 Changelog]]

## LLM 更新时的标准动作

| 步骤 | 动作 |
|-----|------|
| 1. 阅读 | 读 inbox 中新来源 + 相关已有实体页 |
| 2. 提取 | 识别：新概念、对已有实体的补充、矛盾、可删除的过时信息 |
| 3. 更新实体 | 修改 `07-实体百科/` 或 `04-玩家库/` 中的页面 |
| 4. 更新交付物 | 必要时修订阅读路线、风险地图、季度跟踪 |
| 5. 归档来源 | 将来源移至 `sources/processed/` 并标注处理日期 |
| 6. 写 Changelog | 在 [[更新日志 Changelog]] 追加条目 |

## 本项目的 Wiki Prompt 位置

- 完整更新指令：`wiki/scripts/wiki_update_prompt.md`
- 辅助脚本：`wiki/scripts/wiki_update.py`

## 与 agent 代码的分工

| 层级 | Wiki | agent/ |
|-----|------|--------|
| 研究 | 引擎对比、策略演进、行业动态 | — |
| 规范 | 最佳实践、风险清单 | `references/` |
| 执行 | — | `scripts/`、`templates/` |
